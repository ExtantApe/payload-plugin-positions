# Decisions

Dated decisions for this repo, newest last.

- 2026-11-22: created from the ops starter kit, area `co-plugins`.
- 2026-11-22: created as a skeleton on our side (owner, via Simon: "Do you need to create repos for Garfunkel? If so, please do so"). Scope to come from Captive Origins. npm name @extantape/payload-plugin-positions (D131). MIT, EXTANT APE. Contributions from co/ branches; only the owner merges (D256).
- 2026-11-22: description and scope from Captive Origins (via Simon): scoped, dated grants with host-defined types, grant rules and an audit trail; a refuse-grant hook so a host can keep minors from holding positions.
- 2026-11-22: first version built for Captive Origins' account model (positions are scoped grants in one table, in an agnostic plugin). Design choices: `canGrant` fails closed on anything but exactly `true`; `refuseGrant` is a host veto that also binds server code that skips access; revoked and expired are final; grants are never deleted; helpers take `payload` first because they have to read the table.
- 2026-11-22: review fixes from EXTANT APE (bottle 115). Giving more is a grant: resume and extension need `canGrant` and the veto. `refuseGrant` is required, with `false` as the opt-out. History is append-only and written only by the plugin. Notes are staff-only. Self-grants are off unless the host opts in.
- 2026-11-22: second review from EXTANT APE (bottle 118). Notes and history have their own read option, `canReadPrivate`, closed by default. History is written in the grant's transaction and the plugin refuses to run without one unless the host opts out.
- 2026-11-23: the host veto no longer shows its reason to a signed-in granter (owner, relayed: "Fix in 0.1.1 (Recommended)"). This first fix still left an oracle: a granter got 403 for a minor and 201 for an adult, and 403 against 200 on resume and extension. Superseded by the next entry.
- 2026-11-23: pending grant, check at accept (owner, in the reviewer's chat: "Pending grant, check at accept (Recommended)"). Every grant is recorded as pending, the same for everyone, and the veto runs when the holder accepts, as in the organizations plugin. The granter never sees the result. A resume or an extension also puts the grant back to pending, so the granter's answer is the same for every holder. Also in 0.1.1: `refuseGrant` must be a function or exactly `false`; a `canRead` or `canReadPrivate` answer of `{}` or `[]` means no; the revoke-only refusal is the standard Forbidden. What remains visible: a granter can see a grant stay pending, which looks the same whether the holder has not answered or was refused.
- 2026-11-23: the pending-grant change ships as 0.2.0, not 0.1.1 (owner: "0.2.0 (Recommended)"). It is breaking: `RefuseArgs.action` is narrower, `PositionStatus` and `AuditName` gain `pending` and `accept`, and hosts need an accept step. Extending a paused grant leaves it paused. Read answers from `canRead` and `canReadPrivate` count only as `true`, `false` or a real `where`.
- 2026-11-23: only the plugin sets a grant to pending. A client-set `pending` is refused on create and update, over every API, because paused to pending skipped the grant check (and active to pending wrote no history). Resume and extension still go to pending by the plugin's own hand. A `where` from `canRead` or `canReadPrivate` may use only Payload's own operators (`validOperators` in the installed payload, 3.92) plus `and` and `or`; any other key fails closed.
- 2026-11-23: bulk updates of grants are refused, by a `beforeOperation` hook that runs before access and every other hook. Reason: Payload's bulk update catches a row's error and commits, so the `updatedAt` bump from the write lock survived a refused accept and showed which holders were vetoed (a minors oracle); it also broke the nothing-partial promise. Bulk has no real use here, since every change needs its own history row, veto and audit hooks, so refusing beats claiming late. Breaking, noted in the changelog. A host `where` naming a field the collection lacks, or dotting into a text field, returns no rows instead of a 500.
